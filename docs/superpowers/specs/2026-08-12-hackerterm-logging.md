# HackerTerm 日志子系统设计

> 状态：设计草案，待实施。
> 触发：用户 2026-08-12 决定「日志写到文件比较好，后续可以追踪；但日志不要影响性能，可以异步 batch」。

## 1. 为什么要做

- 真实用户报障时，唯一可靠的证据来源。M0 阶段每查一个 bug 都要用户手动截图回报，一轮一天。
- 用户此前明确要求：「操作一定要留日志（方便后续企业版本，也方便用户后续做历史自动提示，还有给 AI）」。
- V2 企业版需要把诊断信息上报到管理端。

## 2. 两条不可妥协的红线

### 2.1 载荷内容永不入文件日志

**终端内容里有密码。** 用户会敲 `mysql -p<密码>`、会在 `sudo` 提示后输入、会粘贴 API key
和私钥。把 PTY 载荷写进日志文件，等于在用户硬盘上生成一个明文凭据库。

**硬规则：文件日志只记大小、条数、时序、错误，永不记载荷字节。**

当前 `src/ui/browser/diagnostics/byte-throttle.ts` 的 `createOnDataLogger` 打的是按键内容的
十六进制预览（`hexPreview`）。这在 M0 排障期是对的（用户本人在场、只进 console），
**但它绝不能跟着文件日志发布**。实施时必须把「内容级诊断」与「文件日志」在类型上就分开，
不能靠约定。

同类需要脱敏的还有：主机名、用户名、绝对路径、SSH 目标、数据库连接串。

### 2.2 热路径上不许有 logger 调用

**性能风险不在写盘**（异步的，不是瓶颈），**在数据热路径上的调用本身**。

刷屏时 PTY 数据每秒几千条。两个具体陷阱：

1. **字符串在级别判断之前就拼好了**。JS 里 `log(\`收到 ${n} 字节\`)` 的模板字符串在
   函数调用前求值完毕，级别判断救不了它。必须让级别判断发生在消息构造之前
   （VS Code 的 `AbstractMessageLogger` 就是 `if (this.getLevel() <= level)` 先行）。
2. **数据面默认一条都不打**。只按固定间隔打计数汇总（当前
   `INCOMING_DATA_SUMMARY_INTERVAL` 这类机制的思路是对的，保留）。逐条打印只在
   显式开启的诊断模式下允许。

## 3. 架构：每个进程写自己的文件

**不汇总到单一写入方。** 理由是失败模式：**最需要的日志恰恰是崩溃时那些**。若所有日志
经核心进程转发，核心一挂就全部丢失——而那正是最需要日志的时刻。VS Code 同样是每进程
一个文件。

| 进程 | 实现 | 说明 |
|---|---|---|
| Rust 核心 | `tracing` + `tracing-appender` 非阻塞写 | 后台写线程 + 无锁队列，现成的异步 batch |
| 主进程 | Node 写流 + 显式攒批 | 定时或满量冲刷 |
| core-host | 同主进程 | |
| 渲染进程 | **不能直接写文件** | 沙箱限制，且 ESLint 禁止 `ui/browser` 引 `node:*`；经 IPC 交主进程代写 |

渲染进程的日志量必须小——这正是 §2.2「数据面不逐条打」的另一个理由。

## 4. 文件与轮转

参考 VS Code 的实测参数（`spdlogLog.ts`）：**6 个文件 × 5MB，总预算 30MB**。

- 按会话建目录（时间戳命名），便于定位「哪一次运行出的问题」。
- 每进程一个文件：`main.log` / `core-host.log` / `renderer.log` / `core-rust.log`。
- 超出预算按最旧优先删除。

具体数值先按 VS Code 取值作为**暂定值**，写进常量模块（本项目禁止魔数），
真机跑出实际增长速率后再定。

## 5. 日志级别

`error` / `warn` / `info` / `debug` / `trace`。默认 `info`。

- `info` 及以上：会话生命周期、连接建立/断开、错误、崩溃事件。
- `debug`：控制面方法调用（不含载荷）。
- `trace`：数据面计数汇总。**逐条载荷诊断不属于任何级别，单独开关控制且只进 console。**

## 6. 一键导出诊断包

产品功能：菜单里一个入口，打包当前会话目录 + 环境信息（版本、OS、CPU、GPU 状态）
成一个 zip，用户直接发给支持。

导出前必须跑一遍脱敏。V2 增加上传到管理端。

## 7. 与现有代码的关系

- `src/ui/browser/diagnostics/log.ts`：用户已决定去掉页面日志框、改走 console。
  文件日志是在此之上新增的一层，**不是替换 console**——开发时 console 更方便。
- `src/main/startup-timing.ts` 的启动时间线：应当进 `info` 级文件日志，这正是
  「用户报启动慢」时最需要的东西。
- 上一轮新装的错误捕获（`uncaughtException` / `child-process-gone` /
  `render-process-gone` / `window.onerror`）：全部进 `error` 级，**这是本子系统
  最高价值的内容**。

## 8. 待定

- 攒批的冲刷间隔与阈值
- 会话目录的保留策略（保留几次运行）
- 崩溃时如何保证缓冲区里的日志能落盘（异步 batch 与崩溃现场的固有矛盾——
  `error` 级是否应当同步写，需要实测代价后决定）

第 8 条最后一项要特别注意：**异步批量写和「崩溃前最后几条日志」天然冲突**。
崩溃时缓冲区里没冲刷的内容会丢，而那几条恰恰是最关键的。需要在实施时验证代价。
