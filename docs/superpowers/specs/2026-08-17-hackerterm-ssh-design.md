# HackerTerm SSH 层设计

> 状态：设计草案，未实现。
> 触发：用户 2026-08-17 明确「ssh 是核心场景，基本上终端都是连接 ssh 的。
> ssh 组件和终端结合，然后 ssh 组件网络这块都要核心设计」。
>
> 本文档的结论**来自阅读 russh 与 RFC 4254 的实际实现**，不是通用 SSH 常识。
> 凡是推断而非实测的地方都已标注。

## 0. 这份文档为什么重要：它改变了优先级

M0 阶段所有的测量与优化都跑在**本地 PTY** 上。如果绝大多数标签页都是 SSH，
那么已经查清的这几件事**只作用于「本地 shell」这一小部分场景**：

| 已查清的事 | 对 SSH 是否适用 |
|---|---|
| ConPTY 吞吐 2.3 MiB/s | **不适用**——SSH 会话不经过本地 ConPTY |
| `PSEUDOCONSOLE_PASSTHROUGH_MODE` | 不适用（且对 PowerShell 本身也无效，见任务 #31） |
| 随包分发 ConPTY（任务 #32） | 不适用 |
| 我们的 IPC 0.36ms | **占比可忽略**——RTT 30ms 的服务器上它只占 1.2% |

SSH 会话的路径是：`russh` 连远端 → 在**远端**申请 PTY → 字节流经网络回来。
**本地 ConPTY 完全不参与。**

## 1. 决定「丝滑」的东西完全不同

| | 本地 shell | SSH |
|---|---|---|
| 按键往返 | 1.10ms（实测：ConPTY 0.71 + 我们 0.36） | **网络 RTT 主导**，10–200ms |
| 吞吐上限 | ConPTY（实测 2.3 MiB/s） | 加密算法 + TCP + SSH 通道窗口 |
| 主要故障 | 渲染、IPC | **断线、重连、网络抖动、休眠唤醒** |
| 我们能优化的部分 | 33% | **通常 < 5%** |

**结论：SSH 场景下继续优化本地 IPC 没有意义。** 工程量应当投向连接管理、
多路复用、故障恢复——也就是用户说的「网络这块要核心设计」。

## 2. 最关键的发现：russh 的窗口补充与消费解耦

读 `russh/src/session.rs` 的 `adjust_window_size`：

```rust
pub fn adjust_window_size(&mut self, channel: ChannelId, data: &[u8], target: u32) -> ... {
    if data.len() as u32 <= channel.sender_window_size {
        channel.sender_window_size -= data.len() as u32;
    }
    if channel.sender_window_size < target / 2 {
        push_packet!(self.write, {              // 立刻补满窗口
            self.write.push(msg::CHANNEL_WINDOW_ADJUST);
            (target - channel.sender_window_size).encode(&mut self.write)?;
        });
    }
}
```

**窗口补充由「收到多少字节」驱动，与消费方是否处理完毫无关系。** 剩余窗口低于
`target/2` 就立刻补满。

### 后果：我们的背压传不到远端

现有本地 PTY 的流控模型是「渲染层 ack → Rust 暂停读 PTY → 子进程被内核阻塞」，
背压一路传到数据源头。**SSH 上这条链断了**：我们暂停消费，russh 照样补窗口、
远端照样发。数据只能堆在 russh 内部缓冲里。

两种坏结局，取决于 russh 内部通道是有界还是无界：
- 无界 → **内存无限增长**（`cat` 一个 10GB 文件直接吃爆内存）
- 有界 → 会话任务被堵住 → **同一条 TCP 上所有其他会话一起卡死**

第二种正是任务 #29（控制面同步阻塞）的跨网络版本。**同一个架构缺陷，换了个地方。**

### 待验证

`adjust_window_size` 的**调用点**不在已读的三个文件里（`channels/mod.rs`、
`session.rs`、`client/mod.rs`），推测在 `lib_inner.rs` 的收包路径上。
实现前必须读到调用点，确认：
1. 是否每收到一个 `CHANNEL_DATA` 就无条件调用；
2. russh 把数据递给消费者用的是有界还是无界通道；
3. `Config::window_size` / `target_window_size` 的默认值是多少。

**在读到之前，本节的后果分析属于推断，不得当作既定事实。**

## 3. 第二个发现：窗口耗尽时发送端无限期挂起

读 `russh/src/channels/mod.rs` 的 `reserve_writable_chunk`：

```rust
loop {
    let mut window_size = self.window_size.value.lock().await;
    let writable = max_packet_size.min(*window_size).min(remaining);
    if writable > 0 { *window_size -= writable; return Ok(writable); }
    let notified = self.window_size.notifier.notified();
    drop(window_size);
    notified.await;          // 窗口为 0 就一直等，没有超时
}
```

符合 SSH 语义（这就是背压），但**没有超时**。远端若永不发 `WINDOW_ADJUST`
（网络黑洞、远端进程卡死、中间设备吞包），写操作永久挂起且不报错。

**这与我们刚修的「ack 丢失导致终端永久冻结」是同一类故障。** 本地那次的解法是
停摆看门狗：超时后强制清零 + **上报事件**（绝不静默自愈）。SSH 这边需要等价物，
且必须能区分「远端真的很慢」和「通路已死」。

## 4. 连接模型：一条 TCP 承载多个会话

用户核心要求之一是「10+ 并发会话」。两种模型：

| | 每会话一条 TCP | 一条 TCP 多通道（类 OpenSSH ControlMaster） |
|---|---|---|
| 开第 N 个标签 | 每次完整握手（TCP + KEX + 认证），秒级 | 只开一个通道，毫秒级 |
| 资源 | N 倍 socket、N 份加密上下文 | 1 份 |
| 故障隔离 | **一条断只影响一个标签** | 一条断，全部标签一起断 |
| 头阻塞风险 | 无 | **有**（见 §2） |

**倾向多路复用**，因为「开标签要等几秒」直接违反丝滑要求。但必须解决头阻塞，
否则一个慢消费者会拖垮同连接上的所有会话。

**这一条与 §2 是同一个问题的两面**：多路复用的价值取决于我们能否让每条通道
独立背压。若做不到，宁可退回「每会话一条连接」——**慢一点好过全部一起卡死**。

## 5. 三层流控如何协同

从下往上：**TCP 拥塞窗口 → SSH 通道窗口 → 我们的高低水位**。

现状：我们的高水位 1 MiB，SSH 常见初始窗口 64 KB 量级、最大包 32 KB（RFC 4254
要求最大包 ≥ 32768）。**同一数量级，正是两套流控最容易互相干扰的区间。**

必须明确定义**谁是权威**。倾向：**我们是权威**，SSH 窗口配合我们——即由消费进度
驱动窗口补充，而不是由收包驱动。这需要绕过或改造 russh 的默认策略（§2）。

必须在设计阶段就想清楚，不能实现完再测——两套独立流控互相等待的死锁，
是典型的「看着都对、就是不动」，正是本项目最难查的故障类型。

## 6. 断线与重连：真正的体验分水岭

本地 PTY 不会「断线」，SSH 会，而且很频繁：Wi-Fi 切换、VPN 重连、笔记本休眠唤醒、
运营商 NAT 超时。

需要定义：
- **keepalive**：间隔多久、几次不通判定断开
- **重连策略**：指数退避、最大重试
- **会话恢复**：重连后能否恢复原会话？纯 SSH **不能**（远端进程随连接死）。
  要真正做到需要远端配合（tmux/mosh 思路）。**V1 应当明确：重连 = 新会话，
  滚动内容保留在本地但远端上下文丢失。** 不要给用户虚假承诺。
- **UI 语义**：断线时标签页显示什么、能否重试、滚动内容是否保留

## 7. 认证

用户早期已明确：支持密码与密钥文件，并**为「远程派发」留口子**（V2 由管理端下发，
V1 不做但架构要留）。

需定义：密钥格式支持范围、加密私钥的口令输入时机、agent 转发是否支持、
主机密钥校验策略（首次信任？严格校验？——**安全与体验的取舍，需要用户拍板**）。

## 8. 加密算法选择

- **AES-GCM**：有 AES-NI 硬件加速的机器上约 1 GB/s
- **ChaCha20-Poly1305**：无 AES-NI 时更快（老机器、部分 ARM）

应当按运行时 CPU 能力选择，而不是写死。**但在 RTT 主导的交互场景下这个选择
几乎不影响手感**，只在大文件传输（SFTP）时才显著。**别为它过度投入。**

## 9. 与现有架构的接入点

好消息：**协议层不用大改**。现有 `session.open` 已有 `shell` / `cwd` 字段，
SSH 会话可以复用同一套 `session.open` / `session.resize` / `session.close` /
`session.ack` / 数据面 MessagePort。差别在 `SessionOpenRequest` 需要增加连接目标
（主机、端口、认证方式）。

数据面完全复用——渲染层不关心字节来自本地 PTY 还是远端。**这正是当初把
数据面设计成裸字节流的价值。**

## 10. 必须实测、不许假设的清单

本项目的教训是「看着对、不报错、就是不工作」。以下几条在实现前后都必须有
能变红的测试：

1. **背压是否真的传到远端**：远端灌数据、我们停止消费，观察内存是否增长、
   远端是否被阻塞。**这是 §2 的判决实验。**
2. **多路复用下的头阻塞**：一条通道的消费者卡住，其他通道是否仍然流畅。
3. **窗口耗尽的超时行为**：制造远端不发 `WINDOW_ADJUST` 的场景，确认不会永久挂起
   且有事件上报。
4. **断线恢复**：拔网线 / 挂起进程 / 丢包，确认状态正确、有明确提示、不静默卡死。
5. **10+ 并发 SSH 会话的串扰**：复用本地已有的双向串扰矩阵测试（`e2e/concurrency-crosstalk.e2e.ts`），
   把数据源换成 SSH。**那套矩阵已经用三次变异验证过有效。**

## 11. 待定（需要用户拍板的）

- 主机密钥校验策略：首次自动信任（体验好）vs 严格校验（安全）
- 多路复用 vs 每会话独立连接（取决于 §2 能否解决）
- 是否支持 agent 转发
- SFTP 是否进 V1（文件管理需要，但用户说过「文件管理前期只做右键打开当前目录」）
