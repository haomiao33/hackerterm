# HackerTerm 产品需求（大方向）

> 状态：草案，待拍板 · 日期：2026-08-07
> 本文只定大方向。细节见 §9 待议清单。

---

## 1. 一句话

> **终端、数据库、文件管理，都在一个软件里管。每个功能开在自己的 Tab 里。**

用户今天要装三个软件：终端（Xshell / iTerm2）、数据库（Navicat）、
文件传输（WinSCP / FinalShell）。三套连接配置，三个图标。

**不是说不用切换** —— 切 Tab 是正常的，本来就该切。
区别是：切的是同一个软件里的 Tab，不是三个软件的窗口。

---

## 2. 四条核心（重点关注，做不到产品就不成立）

这四条是产品的底线，排期紧张时**优先保这四条，其它都可以砍**。

### ① 都在同一个软件里管
终端、数据库、文件管理在一个软件里，一棵连接树管所有连接。

### ② SSH 要丝滑 —— 数据量大不能卡

这是终端最容易翻车的地方。必须扛住的场景：

| 场景 | 要求 |
|---|---|
| `cat` 一个几十 MB 的二进制文件 | 不卡死、不假死，能 `Ctrl+C` 立刻中断 |
| `tail -f` 高速刷屏的日志 | 持续跟得上，不掉帧，界面还能操作 |
| 同时开 10+ 个会话，多个在刷屏 | 每个都流畅，互不影响 |
| 大文件传输的同时敲命令 | 敲命令不卡顿 |
| 敲键盘 | 按下到显示 < 一帧（16ms） |
| 屏幕上没有输出时 | CPU 占用 0%，风扇不转 |

**必须做并发压力测试，不能只测单会话。**

### ③ 数据库不能卡 —— 尤其是结构解析和自动提示

这是 DataGrip 被骂最多的地方：**自动提示做得好，但刷新数据库结构能卡死人。**
几十个库、几百张表的时候，转圈半天甚至整个界面无响应。

| 场景 | 要求 |
|---|---|
| 连上一个有 **几十个库、几百张表** 的实例 | 树能立刻展开，**不等全部加载完**（用到哪个加载哪个） |
| 刷新数据库结构 | **后台加载，界面不冻结**，可以随时取消 |
| SQL 自动提示 | 表名列名秒出，**不能因为结构还没加载完就没提示** |
| 查询返回几十万行 | 不卡死，滚到哪加载到哪 |
| 执行慢查询时 | 界面不冻结，能取消执行 |

**自动提示要做到 DataGrip 的水平，结构加载要比 DataGrip 快。这是我们在数据库上的核心承诺，不比功能多。**

### ④ 不能崩溃

**做法：一个 Tab 一个进程。**（你提的，我认为是对的）

| 承诺 | 说明 |
|---|---|
| 一个 Tab 崩了，其它 Tab 照常工作 | 崩的那个显示「已崩溃，点击重开」 |
| 界面崩了，SSH 会话不断 | 重开后连接还在，正在跑的命令还在跑 |
| 画面出问题不白屏 | 自动切兼容模式并提示 |
| 异常退出后能恢复现场 | 窗口布局、打开的 Tab、每个 Tab 的目录 |

> **代价**：一个 Tab 一个进程会更吃内存。需要定一个上限，
> 比如「开 20 个 Tab 内存不超过 X」，这个数值待定（见 §9）。

## 3. 核心机制：左边一棵树，管所有连接

```
┌──────────────────┬───────────────────────────────────────────────┐
│ 🔍 搜索           │▐ web-01 × │▐ orders_db × │▐ zsh × │  +   🤖 │
│                  │  ↑红·生产    ↑红·生产       ↑灰·本地           │
│                  ├───────────────────────────────────────────────┤
│ ▐ 生产环境  ▼     │ [root@web-01 ~]# tail -f app.log              │
│   ● web-01       │                                               │
│   ○ web-02       │                                               │
│   🗄 orders_db    │                                               │
│                  │                                               │
│ ▐ 测试环境  ▼     │                                               │
│   ○ test-01      │                                               │
│   🗄 test_mysql   │                                               │
│                  │                                               │
│ ▐ 本地      ▼     │                                               │
│   🖥 zsh          │                                               │
│   🗄 dev_mysql    │                                               │
└──────────────────┴───────────────────────────────────────────────┘
   ▲ 左边按分组着色              ▲ 顶部 Tab 继承所属分组的颜色
```

树里可以放三种东西：**SSH 连接**、**数据库连接**、**分组**。
两种连接**各自独立创建、独立配置**，谁也不依赖谁。

### 每个功能开在自己的 Tab 里

| 打开的东西 | 开出来是什么 Tab |
|---|---|
| SSH 连接 | 终端 Tab |
| 数据库连接 | 查询 Tab |
| 管理文件 | 文件 Tab |

Tab 可以任意分屏并排看，也可以拖出去成独立窗口。

### 右键就是主要入口

| 右键位置 | 菜单 |
|---|---|
| **树的空白处 / 分组上** | 新建 SSH 连接 · 新建数据库连接 · 新建分组 · 设置分组颜色 |
| **一个 SSH 连接** | 打开终端 · **管理文件** · 编辑 · 复制 · 删除 |
| **一个数据库连接** | 打开查询 · 编辑 · 复制 · 删除 |
| **终端窗口里 / 终端 Tab 上** | **管理文件**（开当前这台服务器的文件 Tab） |

**「右键终端 → 管理文件」是最能体现产品价值的一处**：
你正连着 web-01，想看日志文件，右键就开一个文件 Tab，不用去开 WinSCP。

## 4. 连接的组织方式

每个连接（SSH 和数据库都一样）可以设置：

| 属性 | 说明 |
|---|---|
| **标签** | 一个连接可以打多个标签（如 `线上` `订单` `华东`），可按标签筛选 |
| **颜色** | 单独指定颜色，覆盖所属分组的颜色 |
| **分组** | 可嵌套的多级分组，拖拽移动 |
| **排序** | 手动拖拽排序，也可以按名称/最近使用自动排 |

### 颜色规则

**分组带颜色，Tab 继承分组的颜色。**

- 生产环境标红 → 侧栏该分组是红的，从它开出来的**所有 Tab 也是红的**
- 一眼看出当前 Tab 是不是生产环境，**防止在生产机上误操作**
- 连接单独指定的颜色优先于分组颜色

## 5. SSH 认证方式

| 方式 | V1 | 说明 |
|---|---|---|
| **密码** | ✅ | 存本机系统钥匙串 |
| **密钥文件** | ✅ | 支持带口令的密钥 |
| **远程派发** | ❌ 留口子 | 由企业管理端下发，V1 不做 |

**V1 必须做的一件事**：每个连接标记来源是「本地」还是「远程下发」。
V1 全部是「本地」，但这个标记和对应的界面状态（远程下发的不可编辑、带 🔒）
现在就要有，否则 V2 要改遍所有连接相关的界面。

## 6. 快捷键

| 要求 | 说明 |
|---|---|
| **有一套默认键位** | 覆盖软件的全部功能，开箱即用 |
| **跟随系统习惯** | macOS 用 `Cmd`，Windows / Linux 用 `Ctrl`，各平台一套，符合各自平台的习惯 |
| **可迁移** | 提供预设方案一键切换：**DBeaver · DataGrip · Xshell · iTerm2 · Windows Terminal · VS Code** |
| **可修改** | 有一个快捷键管理界面，任意重绑，冲突时明确提示，可重置 |

> 待定：和 shell 冲突的键（尤其 `Ctrl+R`）要不要抢过来。见 §9。

## 7. 皮肤统一

**一套皮肤同时管终端、数据库、文件管理和整个界面。**

不是"终端有终端的配色，数据库有数据库的配色"——换一次肤，全部一起变。

包括：终端配色、侧栏、Tab 栏、数据库结果表格、SQL 高亮、文件列表、各种面板。

可改的还有：字体（**中文字体可单独设置**）、字号、行高、背景不透明度、
光标形状、内边距、深浅色跟随系统。

## 8. 数据库要做的事

除了 §2 ③ 说的「快」，功能上必须做到这几块：

### 8.1 建库建表（DDL）

| 能力 | 说明 |
|---|---|
| 新建 / 修改 / 删除 **库** | 字符集、排序规则可选 |
| 新建 / 修改 / 删除 **表** | 可视化建表：列名、类型、长度、默认值、非空、注释 |
| 索引 | 建普通索引、唯一索引、组合索引 |
| 外键 | 建、改、删 |
| 视图 | 至少能看，能建更好 |
| **执行前先看 SQL** | 所有可视化操作，执行前都能看到实际要执行的 SQL，可以复制走 |

最后一条很重要 —— 用户不信任"黑盒改我的表"，让他看到 SQL 才敢点确定。

### 8.2 导入导出（用数据库自带的工具）

> **关键决策：直接调用系统自带的 `mysqldump` / `mysql` / `pg_dump` / `pg_restore`，
> 不自己造。** 这样导出的文件和命令行导出的完全一致，别人拿去用不会出兼容问题。

**导出**

| 导出什么 | 格式 |
|---|---|
| 整库 / 选中的表 | **mysqldump / pg_dump 原生格式**（可选：只结构 / 只数据 / 结构+数据） |
| 查询结果集 | CSV · JSON · SQL · Excel |

**导入**

| 导入什么 | 说明 |
|---|---|
| `.sql` 文件（含 dump 文件） | 流式执行，**几百 MB 的文件也不能卡死**，显示进度、可随时取消 |
| CSV | 导进指定的表，可映射列 |

**必须做好的细节**
- 导入导出全程显示进度和预计剩余时间
- 出错时明确告诉用户第几行出错、错在哪，而不是笼统报个失败
- 导出时如果本机没装 `mysqldump` / `pg_dump`，要给出明确提示和解决办法

### 8.3 数据库信息

连上之后能看到这个库的基本情况，不用自己敲 SQL 查：

版本 · 字符集 · 已运行时长 · 当前连接数 / 最大连接数 ·
库的大小 · 表数量 · 最大的几张表 · 当前正在执行的会话

## 9. 服务器信息（信息探测）

**SSH 连上之后，自动探测并显示这台服务器的情况。**

这是 FinalShell 最受欢迎的功能之一，国内运维很吃这一套。

| 显示什么 | |
|---|---|
| CPU | 使用率、核数、型号、负载 |
| 内存 | 已用 / 总量、Swap |
| 磁盘 | 各挂载点已用 / 总量、**快满了标红** |
| 网络 | 实时上下行速率 |
| 系统 | 发行版、内核版本、开机时长 |
| 进程 | 占 CPU / 内存最高的几个 |

**要求**
- 探测在后台跑，**不能影响终端输入**
- 可以关掉（有些机器不希望被周期性执行命令）
- 探测频率可调
- 探测失败（比如权限不够、命令不存在）时安静降级，不弹错误框骚扰用户

**放在哪里**：待议（见 §12）—— 可以是终端 Tab 里的一个可折叠侧边栏，
也可以是右键连接单独开一个「服务器信息」Tab。

## 10. V1 范围

### 做

| 模块 | 做什么 |
|---|---|
| **终端** | 本地 Shell + SSH，多标签、分屏、主题、快捷键 |
| **连接树** | 统一管理 SSH 和数据库连接；标签、颜色、分组、排序、搜索、右键；支持从 Xshell / FinalShell / PuTTY 导入 |
| **数据库** | **只支持 MySQL 和 PostgreSQL**。查询、改数据、看表结构、自动提示、**建库建表**、**dump 导入导出**、数据库信息 |
| **服务器信息** | SSH 连上后探测 CPU / 内存 / 磁盘 / 网络 / 进程 |
| **文件管理** | 上传下载、直接改远程文件；从连接右键开，也可从终端右键开 |
| **AI** | 看得见终端和数据库，能解释报错、生成命令和 SQL |
| **自动补全** | 命令补全 + SQL 补全，本地和远程都能用 |
| **稳定性** | 一个 Tab 一个进程 |
| **外观** | 统一皮肤、字体、快捷键全部可改 |

### 不做

| 不做 | 理由 |
|---|---|
| MySQL / PG 以外的数据库 | 前期只做这两个 |
| ER 图 / 报表 / 数据同步 / 存储过程调试 | Navicat 的活，比不过也不需要比。（**注意：备份还原不在此列 —— dump 导入导出要做，见 §8.2**） |
| 独立的 FTP 客户端 | 文件管理是配套能力，不是独立产品 |
| 日志分析平台 | 只做"看日志"，不做"分析日志" |
| 插件市场 | V1 最多留个接口 |
| 配置云同步（个人版） | 企业版才做 |
| 移动端 / Web 端 | 分散精力 |

## 11. V2 企业版

用你的原话：**企业对数据库和终端连接有限制，可以下发策略和权限、
管理端下发配置，用户不用一个一个配 SSH 和 DB。**

### ① 配置下发（省事）
管理员在管理端配好服务器和数据库，员工登录公司账号，
**连接树里自动出现，一个都不用自己填。** 人走了管理端一撤，权限立刻没了。

### ② 权限限制（管控）
谁能连哪台机器、谁能连哪个库、哪些库只读、哪些危险命令禁止执行 ——
管理端说了算，客户端改不了。

### ③ 操作留痕（合规）
谁什么时候连了哪台机器、执行了什么命令、跑了什么 SQL，管理端能查。

> ⚠️ 第 ③ 条是我加的，你没提。**如果客户不看重可以砍掉** ——
> 但它影响 V1 要不要提前埋点，需要你明确。

### V1 必须先留好的三个口子

1. **连接来源标记**（本地 / 远程下发）—— 见 §5
2. **每个设置项能显示成「已被公司锁定」**（灰色 + 🔒）。V1 永远不出现，但界面要预留
3. **连接信息和密码分开存** —— 企业版要做到密码不落到员工电脑上，V1 混在一起 V2 就得重做

## 12. 待议清单

**已经定了的**：颜色分组排序标签 · 快捷键方案 · 统一皮肤 · SSH 认证方式 ·
只做 MySQL+PG · 一个 Tab 一个进程 · 四条核心 · 建库建表 · dump 导入导出 ·
数据库信息 · 服务器信息探测。

**还要逐条讨论的**：

| # | 议题 | 需要决定什么 |
|---|---|---|
| 1 | **Tab 管理** | 分屏方式、能不能拖出成独立窗口、Tab 太多怎么办、关闭要不要确认、**开 20 个 Tab 内存上限定多少** |
| 2 | **连接配置表单** | SSH 和 DB 各有哪些字段、跳板和隧道怎么配、导入支持哪几种 |
| 3 | **终端细节** | 回滚多少行、搜索方式、复制粘贴行为、粘贴多行要不要确认 |
| 4 | **数据库** | 结构树怎么组织、能不能直接改数据、写操作怎么防误 |
| 4b | **服务器信息放哪** | 终端 Tab 里的可折叠侧栏 / 单独一个 Tab / 两者都要 |
| 5 | **文件管理** | 双栏还是单栏、能不能直接编辑远程文件、要不要和终端目录联动 |
| 6 | **AI** | 几个入口、能看到什么、能不能自己执行命令 |
| 7 | **自动补全** | 补全内容从哪来、弹窗还是行内、远程怎么补 |
| 8 | **快捷键冲突** | 要不要抢 shell 的键，尤其 `Ctrl+R` |
| 9 | **皮肤** | 内置几套、能不能导入 iTerm2 / DBeaver 配色 |
| 10 | **历史** | 命令历史和 SQL 历史怎么做、要不要跨主机搜索 |

**还不确定要不要做**：

| # | 议题 | 我的初步意见 |
|---|---|---|
| 11 | 日志面板（多机日志合并） | 想做，运维刚需，但可推到 1.0 之后 |
| 12 | 数据库可选择走某个 SSH 连接做隧道 | 建议做，顺手的便利，不是核心卖点 |
| 13 | 生产环境危险命令拦截 | 想做，成本低，运维会喜欢（颜色标红已经定了） |
| 14 | 插件接口 | V1 可以整个推后 |
| 15 | 三平台同时发 | 建议先发两个，第三个跟上 |
